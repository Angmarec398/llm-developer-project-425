# CLAUDE.md

Контекст для продолжения работы над проектом. Это учебный сквозной проект
Hexlet «AI-агент службы поддержки» (курс LLM-инженер, проект 425). Задания
шагов лежат в `docs/*.pdf` — читать их перед выполнением следующего шага,
там точная формулировка задач и критерии сдачи («Результат шага»).

## О проекте

Help Desk-агент — почтовый агент службы поддержки. Принимает обращение по
email, ищет ответ в корпоративной базе знаний (RAG), если ответа нет —
создаёт тикет и сохраняет переписку в БД. Работает целиком внутри контура
Yandex Cloud, без внешних трекеров.

Архитектура:

```
Timer (раз в минуту) ──► email-poller ──► IMAP fetch / SMTP send
                              │
                              ▼ текст обращения
                    ┌─────────────────────────────┐
                    │ Агент в Yandex AI Studio     │
                    │ YandexGPT (Responses API)    │
                    │ + RAG (Search Index)         │
                    └──────────────┬──────────────┘
                                   │ MCP Hub
                                   ▼
                        MCP-инструмент ydb-tickets
                                   │
                                   ▼
                            YDB Serverless
                            ├─ tickets  (обращения)
                            └─ messages (история диалога — пишет poller)

Cron 09:00 ──► Workflow daily-escalation ──► дайджест оператору по почте
```

Стек: YandexGPT через Responses API (в бою у `email-poller` временно
заменён на `deepseek-v4-flash/latest`, см. «Шаг 9» — обе модели доступны
через один и тот же `gpt://<folder>/<model>/latest` URI), YDB Serverless,
инструменты через MCP Hub, деплой через Cloud Functions и Yandex
Workflows, секреты — в Lockbox.
Язык решения: Python 3.12 (примеры в шагах — под Python, но контракт сдачи
от языка не зависит).

## Шаг 5: MCP ydb-tickets (текущее состояние)

- **Схема YDB** — `src/ydb_tickets/schema.sql` (таблицы `tickets`,
  `messages`, PK `messages` — `(user_id, id)`, `ticket_id` — Nullable).
  Применяется через `scripts/init_schema.py` (Python SDK, IAM-токен через
  `YC_IAM_TOKEN`) — второй способ из задачи 1, UI-консоль тоже подходит.
  Скрипт вырезает всё после `--` до конца строки перед разбиением на
  statement'ы по `;` (наивное разбиение ломалось на `;` внутри инлайн-
  комментария `-- ссылка на tickets.id; NULL, ...`).
- **Cloud Function `ydb-tickets`** (`src/ydb_tickets/index.py`) реализует
  `create-ticket` и `list-my-tickets`, диспетчеризация по трём контрактам
  вызова (`_resolve_action`): прямой invoke (`action` в event), HTTP через
  API Gateway (`httpMethod`+`body`), MCP Hub (аргументы инструмента как
  event напрямую, без `action` — определяется по набору ключей). PII
  текста тикета маскируется через `mask_pii` (см. ниже) перед записью.
  Особенность ydb-python-sdk: колонки `Timestamp` при чтении приходят как
  `int` (микросекунды от эпохи), а не `datetime` — конвертация в
  `_format_timestamp`.
- **PII-маскирование** — `src/pii_mask.py`, общий модуль для CF
  `ydb-tickets` и `email_poller.py` (упаковывается в оба zip). Простая
  regex-маскировка email и телефонов; текст сначала маскируется, потом
  пишется в YDB.
- **MCP Hub gateway `ydb-tickets-mcp`** создан через
  `yc serverless mcp-gateway create --tools-file src/ydb_tickets/mcp-tools.yaml`
  (см. ID выше). Оба инструмента в `mcp-tools.yaml` указывают на тот же
  `function_id` — диспетчеризация внутри CF.
- **`email-poller` доработан**: перед вызовом агента читает последние
  `HISTORY_LIMIT` (по умолчанию 10) реплик пользователя из `messages`
  (`ORDER BY created_at DESC`, разворачивает в хронологический порядок),
  пишет входящее письмо (`role=user`, PII замаскирован, `ticket_id=NULL`)
  до вызова LLM. Запрос к Responses API включает `tools: [{"type": "mcp",
  "server_url": MCP_GATEWAY_URL, "require_approval": "never"}]` и историю
  в `input` (role `agent`→`assistant`). После ответа: замеряет
  `latency_ms` (`time.monotonic()` вокруг вызова), достаёт `ticket_id` из
  `output[].type=="mcp_call"` с `name=="create-ticket"` (парсит JSON в
  поле `output` этого элемента), пишет ответ агента (`role=agent`,
  `model`, `tokens_in/out` из `usage`, `latency_ms`, тот же `ticket_id`) и
  UPDATE'ом проставляет `ticket_id` входящей реплике, если тикет заведён
  в этом же цикле. Системный промпт обновлён — описывает, когда вызывать
  `create-ticket`, когда `list-my-tickets`; email отправителя передаётся
  моделью как `user_id` через `instructions` (динамически, на каждый
  запрос).
  Деплой поллера теперь требует **все** переменные окружения разом
  (версия не наследует их от предыдущей): `YC_FOLDER_ID`, `IMAP_HOST`,
  `SMTP_HOST`, `IMAP_USER`, `SMTP_USER`, `HELPDESK_MAILBOX`,
  `OPERATOR_EMAIL`, `MCP_GATEWAY_URL` + секреты `IMAP_PASSWORD`/
  `SMTP_PASSWORD` (`email-credentials`) и новые `YDB_ENDPOINT`/
  `YDB_DATABASE` (секреты `ydb-endpoint`/`ydb-database`). SA — тот же
  `ai-studio-sa`, роль `ydb.editor` на запись в YDB уже была выдана на
  шаге 3 (отдельно выдавать не потребовалось). Таймаут увеличен с 30s до
  180s — запрос с MCP-инструментом занимает больше времени (в проверке —
  до ~9с на создание тикета, до ~24с когда агент сначала отвечает текстом
  и затем требуется второй tool-call для `list-my-tickets`).
- **Деплой на Windows**: в PDF команда сборки архива — `zip -j` (Unix); в
  PowerShell аналог — `Compress-Archive` по файлам, скопированным в общую
  временную папку (чтобы пути внутри zip были плоские, как у `zip -j`).
- **End-to-end проверка** (2026-09-22, `director@cif-raz.ru`): письмо
  «Создай тикет, категория bug, текст: не открывается отчёт в личном
  кабинете» → в логах `GOT_UNSEEN=1 → MSG → REQUEST_PAYLOAD → AGENT_OK →
  mcp_call name=create-ticket → SEND_OK`; в YDB тикет и обе реплики с
  `ticket_id`, `model=yandexgpt/latest`, `tokens_in=515`,
  `tokens_out=93`, `latency_ms=6293` (проверено SQL-запросом в консоли
  YDB). Второе письмо «А какой статус у моего тикета?» — в
  `REQUEST_PAYLOAD` видна история из двух предыдущих реплик (multi-turn),
  сработал `list-my-tickets`. Ранее отмеченная «выдумка про ЭДО Диадок» —
  оказалась реальным текстом из подписи отправителя, а не галлюцинацией
  модели.

### Проверка критериев сдачи («Результат шага», начата 2026-09-23)

Формулировки — из чек-листа «Результаты 6 шага», сверяем пункт за
пунктом, не сдаём шаг, пока все не подтверждены:

1. **Workflow отрабатывает по расписанию, письмо-дайджест доходит** —
   ⚠️ принято как выполненное решением пользователя 2026-09-23, без
   финальной проверки автозапуска. Ручной запуск и доставка письма
   подтверждены (2026-09-22). При проверке 2026-09-23 обнаружено, что
   расписание из-за перепутанного порядка полей cron срабатывало
   **каждый час**, а не раз в сутки (см. выше) — исправлено на `0 0 6 *
   * *` (06:00 UTC = 09:00 МСК). Автозапуск по **исправленному**
   расписанию не дожидались (ближайший — 2026-09-24 06:00 UTC); если
   в будущем понадобится подтвердить, что оно всё ещё срабатывает раз в
   сутки: `yc serverless workflow execution list --workflow-name
   daily-escalation` и посмотреть даты в id (`...-schedule-YYYY-MM-
   DDT06:0X:00Z`) — не должно быть больше одного срабатывания в сутки.
2. **Тикеты переходят в `escalated`, повторно в дайджест не попадают** —
   ✅ подтверждено 2026-09-23: `SELECT status, count(*) FROM tickets
   GROUP BY status` в консоли YDB — `escalated: 2`, `open` отсутствует.
   И `select_overdue`, и `mark_escalated` фильтруют строго `WHERE status
   = 'open'`, поэтому уже эскалированные тикеты структурно не могут
   попасть в выборку снова — этим объясняется, что почасовые срабатывания
   workflow за сегодня (пока не был исправлен cron, см. выше) не создали
   дублей: `select_overdue` находил 0 строк и шёл сразу в `done`.
3. **В трейсах виден каждый шаг (вход/выход, длительность, токены)** —
   ✅ подтверждено 2026-09-23, но данные разнесены по двум разным
   консолям Yandex Cloud:
   - **YC Logging** (лог-группа `default`, ресурс `serverless.workflow`,
     id `dfq9949uhkq7c1hae9lb`): `Execution started/finished` и `Step
     started/finished` на каждый шаг отдельно, с `execution_id`,
     `step_id`, `duration`/`execution_duration` (пример — шаг
     `build_digest`, `2026-09-22T15:36:57Z`, `duration: 1.808783873s`).
     Токенов здесь нет — `jsonPayload` шага `aiStudioAgent` их не
     содержит в принципе (проверено по полному экспорту лога).
   - **AI Studio → раздел «Логирование»** (не «Responses API» — там нет
     ни промптов, ни мониторинга по `promptTemplateId`): по каждому
     вызову модели виден полный объект ответа, включая
     `usage.input_tokens`/`output_tokens`/`total_tokens` (пример —
     ответ `id=2cb5bc57-7d9c-4323-b552-5f98c43a274e`:
     `input_tokens=412, output_tokens=117, total_tokens=529`, тот же
     дайджест по двум тестовым тикетам).
   Итого: вход/выход/длительность — в YC Logging по `execution_id`,
   токены — в «Логировании» AI Studio по `response id`; при защите шага
   стоит явно проговорить, что это два разных источника, а не один.
4. **Объяснение разницы pull-poller (шаг 4) vs workflow по расписанию
   (шаг 6)** — ✅ зафиксировано 2026-09-23. Pull-poller (`email-poller`):
   timer каждую минуту, сам идёт во внешнюю систему (IMAP) проверить
   события, реагирует на непредсказуемые единичные письма с низкой
   задержкой, логика — императивный код в одной функции. Scheduled
   workflow (`daily-escalation`): cron раз в сутки, обрабатывает пачкой
   накопленное состояние **своей** БД (не внешний поток), многошаговый
   процесс с ветвлением/LLM/апдейтом описан декларативно в YAML — retry,
   трейсинг и передача данных между шагами берёт на себя платформа.
   Pull — когда источник не умеет «толкать» события и нужна быстрая
   реакция на каждое; workflow — когда работа периодическая/пакетная над
   своими данными и есть многошаговый процесс, которому нужна
   устойчивость и видимость без ручной оркестрации.

## Шаг 8: фильтры + ИИ-модерация (текущее состояние)

  может частично зацепиться card-регуляркой — полноценно защититься без
  потери recall на реальных картах чистым regex нельзя, решили не
  усложнять дальше.

  `subject`; текст исключений (`MSG_FAIL err=...`) тоже маскируется. В
  [src/ydb_tickets/index.py](src/ydb_tickets/index.py) аналогично
  маскируется `err` в `ACTION_FAIL`. Найдена и закрыта реальная утечка:
  `REQUEST_PAYLOAD` раньше логировал весь `body` запроса к Responses API
  сырым (включая текст письма и email отправителя в `instructions`).
  Сознательно НЕ маскируется `from=`/`to=` в логах и `user_id` в YDB —
  это стабильный идентификатор для сопоставления строк лога с тикетами,
  и он и так не маскируется в самой БД.
- **Guardrail от prompt injection** — в
  [src/ydb_tickets/index.py](src/ydb_tickets/index.py), функция
  `_create_ticket`, вызывается до INSERT. Осознанно размещён именно
  здесь (граница записи), а не в промпте агента и не в `email-poller` —
  единственная точка, через которую тикет попадает в БД, независимо от
  вызывающей стороны (агент через MCP, прямой invoke, гипотетический
  другой клиент). Два уровня:
  1. `_INJECTION_RE` — regex на явные RU/EN паттерны («игнорируй
     предыдущие инструкции», `DROP TABLE`, «удали все тикеты» и т.п.),
     мгновенный блок без LLM.
  2. `classify_text()` → `_classify_llm()` — если regex не сработал,
     текст обращения (немаскированный, для точности) уходит в
     `yandexgpt-lite` через тот же Responses API endpoint, что и основной
     агент (`rest-assistant.api.cloud.yandex.net/v1/responses`,
     `model=gpt://<folder>/yandexgpt-lite/latest`, без tools, один
     user-message). Ответ — одно слово `safe|injection|off-topic`.
  `injection` → исключение `InjectionBlocked`, тикет не создаётся,
  `handle()` возвращает `{"error": "...", "blocked": true}` с HTTP 403
  (при HTTP-контракте) или как есть при прямом invoke; в лог —
  `ALERT_INJECTION_BLOCKED` (текст замаскирован, обрезан до 300 симв.).
  `off-topic` → тикет всё равно создаётся (не блокируем — вдруг просто
  плохо сформулировано), помечается `OFFTOPIC_TICKET` в логе. Сбой/таймаут
  классификатора (10s timeout) — fail-open, `CLASSIFIER_FAIL` в лог,
  вердикт `safe`, чтобы сбой модерации не ронял приём обращений.
  Новая переменная окружения `ydb-tickets` — `YC_FOLDER_ID` (нужна для
  `gpt://` URI и заголовка `x-folder-id`); `--execution-timeout` увеличен
  с 30s до 60s (классификатор — ещё один вызов LLM внутри цикла).
  Опциональная `CLASSIFIER_MODEL` (default `yandexgpt-lite/latest`) — не
  требует отдельного значения в деплое.
  **Промпт классификатора потребовал few-shot примеров**: первая версия
  (только текстовое описание трёх классов) на реальном тесте вернула
  `CLASSIFIER_RAW='safeмощ'` — модель дала верный по подстроке ответ

  классифицировала явно off-topic вопрос («какая завтра погода») как
  `safe`. После добавления 5 примеров-пар «текст → класс» в промпт —
  классификация стала чистой (`off-topic` без мусора, верный класс) с
  первой попытки, без дальнейших итераций.

## Как работаем (важно)

Пользователь проходит учебный курс и просит **пошаговые инструкции**,
которые выполняет сам в своём терминале/консоли — не выполнять команды за
него молча. Формат: команда → объяснение зачем → пользователь выполняет →
присылает вывод → проверяем и даём следующий шаг. Редактирование файлов
самого репозитория (README, конфиги, `.env.example`, код) можно делать
напрямую — это не то же самое, что действия в облачном аккаунте.

**Одно действие за одно сообщение**: не выдавать несколько шагов подряд —
пользователь просил решать одну задачу за один шаг.

Секреты (значения ключей, паролей) никогда не публикуются в чате — только
ID ресурсов (secret_id, version_id, agent_id, folder_id и т.п.).
